# Terminal screen: parity inventory

What the terminal screen does differently from the Ovis browser and from herdr, and what it leaves out, each with the reason. An entry moves between sections, or is removed, when the screen changes. How the screen is compared with herdr's own client is in [visual-parity.md](visual-parity.md).

## Differs from the browser

- Automatic tab names, pin order and the BG state are not shown. Reason: only the Ovis server derives them, and the screen talks to herdr-core only (D2). Worktree workspaces are grouped under their repository's workspace as in the browser, by the same rule (`worktreeGroups` in `shared/worktree-groups.ts`), from the repository facts on the core's terminals.
- Question cards and the readable last turn are not shown; an agent's question is answered by entering its terminal. Reason: they come from the Ovis server (D2).
- There is no "open in Ovis" action and no file preview. Reason: the screen never asks the Ovis server anything, and the browser already has the file viewer and the repo-changes view.
- The agent order of the switcher and of the agent keys, and the state words outside the sidebar, come from the module the browser reads too (`groupAgentRows` in `shared/attention.ts`). Reason: two orders exist today (blocked, working, done, idle in the browser list; blocked, done, working in the roll-up), and the screen must not add a third. The sidebar shows herdr's order instead (below).
- The screen never reads `agent_status` of a tab or workspace; a group's state comes from its panes' states through `rollupStatus` in `shared/attention.ts`. Reason: the snapshot's own roll-up (`rollUp` in `server/herdr-core/snapshot.ts`) orders working above done, and nothing under `src/` reads it.
- Outside the sidebar the screen has no palette of its own: it uses the browser's theme tokens (`tui/theme.generated.ts`, generated from `src/styles.css`). Reason: one theme across Ovis. The sidebar and its rail use herdr's own colour values (below).
- A terminal the screen starts (a new workspace, tab or split) gets herdr-core's own environment plus `TERM=xterm-256color` and `COLORTERM=truecolor`, the two the server also sets on every terminal it starts outside Windows (`COLOUR` in `server/herdr-core/terminal-env.ts`), and not the user's login environment that the server gives its terminals over the core's. The screen passes these two as the `terminalEnv` of the shared `LayoutStore` (`server/herdr-core/layout-ops.ts`). Reason: the server reads the login environment by starting the user's login shell (and `ps` on macOS), and the screen starts no process.
- Before starting the screen or a herdr-core, `ovis tui` reads the environment it was started with from `/proc/self/environ` on Linux and `KERN_PROCARGS2` on macOS. Neither source includes changes Bun made when loading the working folder's `.env` files. If the kernel copy is unavailable, `ovis tui` drops every name assigned by any of the folder's `.env` files, even when the shell set it first, `PATH`, `HOME`, `TERM`, `USER`, `LOGNAME` and `SHELL` included: it cannot tell whose value this process holds. Ovis's settings and hc's usual folders are looked for under the shell's `HOME`, and where that was dropped or never set, under the account's own home from the system's user database, never under one a folder named. The screen filters out the Ovis server's credentials, `HC_SCOPE` and Ovis's own SSH askpass (`HERDR_ASKPASS_TOKEN`, `HERDR_ASKPASS_SOCKET`, and the helper, its `force` and the stand-in display that ssh was given with them; a user's own `SSH_ASKPASS` stays), runs in the install's own folder and is told the folder `ovis tui` was typed in (`OVIS_TUI_CWD`) and the file in which it says which of the terminal's modes it holds (`OVIS_TUI_HOLD`, in the shell's temp folder): when the screen dies by a signal, the launcher writes the terminal's settings back and undoes those modes, no others. A core it starts (only after the user answers yes) gets `coreLaunchEnv` (`server/herdr-core/core-env.ts`), which removes the server's own variables (`SERVER_ENV`, the same list the server keeps from `hc connect`) along with `BUN_BE_BUN`, the pane of another core it may run in (`HC_TERMINAL_ID`, `HC_TERMINAL_SOCKET`, `HC_SCOPE`; the screen keeps the first two, which its refusal to run inside its own core's pane reads), `SSH_TTY`, `SSH_CONNECTION`, `SSH_CLIENT`, `TMUX`, `TMUX_PANE`, `STY`, `WINDOWID`, Ovis's SSH askpass as above, and `SSH_AUTH_SOCK` when `SSH_CONNECTION` is set; `HOME`, the chosen core's `HC_*` and `XDG_*` stay. hc is looked for and asked its `--version` in that same environment: of Ovis's settings only `OVIS_HC_BIN` and `OVIS_HC_BIN_BUNDLED` reach the search, and neither reaches the program. A core the server's `hc connect` starts keeps `SSH_AUTH_SOCK` and the other names (`server/herdr-core/connection.test.ts`), with the login environment laid over it (`coreStartEnv` in `server/herdr-core/terminal-env.ts`); that start is unchanged. Reason: a core hands its environment to every pane for as long as it lives, and `ovis tui` is often run from an SSH login, tmux or a pane of another core, whose names would outlive it in every later pane.
- Recency in the agent order is the screen's own: within a section, the agent the screen has seen longest in its state comes first, counted from when this screen first saw it (every agent of the first snapshot ties and keeps the list's order). Reason: the browser's state-change counters come from the Ovis server (D2), so each client keeps its own.
- The screen writes `herdr.seen` only for the focused pane of the shown tab, Live, drawn in the last frame, with no overlay over it, on a line that is up, while a person is there: the host terminal reported focus in, or, on a host that never reports focus, a key, text, paste or click arrived after that pane's turn ended. It never lowers the label. Reason: one rule with the browser and the Herdr clients (`server/herdr-core/seen-label.ts`); a host without focus reports gives no other proof that someone is in front of it.

## Differs from herdr

- `prefix+g` opens herdr's picker: every terminal under its workspace, searched with `/`. herdr's state filters (`a`, `b`, `w`, `i`, `d`) are not built, and its foot does not name them. Reason: the screen's model holds no state per terminal beyond the agents' order, and the filters' meaning was not measured. In Navigate mode, the configured next and previous tab and workspace keys repeat without the prefix (`n` and `p` select tabs by default); a fixed or explicitly configured Navigate key takes precedence over a derived repeat.

- A terminal that another client sizes is drawn clipped with a notice, and the screen takes a size only after the user's own input in that pane. When that client leaves, herdr-core hands the terminal to a viewer that stays, at the size its attach last advertised; for a pane that repainted at the other client's size that is still that size, so the pane stays clipped with the notice, now alone, until the user types into it. Reason: several clients share one herdr-core, and none may fight over a terminal's size, and a screen that took its size back by itself would move a terminal with nobody typing.
- A window resize or a layout change sends herdr-core no resize. 32 ms after the last change (150 ms while another viewer's size change is still settling), each pane whose rectangle changed closes its attach and attaches again with the new rectangle, so each of them is repainted from the core's first paint; when another client resizes a terminal, its pane repaints the same way, at the size the last client chose: the size herdr-core last reported for the terminal while somebody viewed it, also when that client chose it while the pane was between its close and its new attach. Between the close and the new attach a terminal that only this screen views has no viewer, so it passes through herdr-core's size for an unviewed terminal (200x120): its program is resized twice for one window resize, a few milliseconds apart (1.6 to 12.6 ms, median about 4 ms, over 392 reattaches on herdr-core 0.1.17 and 0.1.18: the time it takes to make the new attach's emulator). A repaint can still take a terminal from a client that chose its size while the repaint's attach was on its way; herdr-core's own event for that attach tells the pane, which then repaints once more at once, so the terminal has the older size for a few milliseconds. Three cases stay as they are until someone types into a pane or changes a window; in each the terminal rests at a size some client chose with its own window, never at 200x120, nothing attaches again, and the next key in a pane gives that pane its own size. (1) A client that only views and whose window is exactly 200x120, attaching while a pane repaints, cannot be told from no client at all (herdr-core's record of the terminal is the same in both cases): the repaint takes the terminal from it, and that client is drawn at the repaint's size with the notice. (2) A client that attaches as a pane's repaint leaves, beside another client that only views and stays: herdr-core often lets the repaint's reply overtake the event of that attach, which then reads like a client coming and going, so the repaint keeps the older size; the new client is drawn at it, and the pane's notice names it. With two attaches written at once and the other one applied first, its event came behind the reply in 298 of 1,184 races on herdr-core 0.1.18 and 324 of 1,195 on 0.1.17 with nobody else viewing, and in 683 of 1,197 and 695 of 1,195 beside a client that stays (an independent run found 245 of 1,197 and 594 of 1,199 there, and runs of a live check of 60 rounds on idle CPUs between 3 and 39); with the screen itself the older size stayed in 2,154 and 2,133 of 5,000 such races. These are records of runs, not bounds: the rate is herdr-core's timing and depends on who else listens to its events. A later set of runs of 1,200 races gave 17 to 41 percent with nobody else viewing and 35 to 51 percent beside a client that stays where every client listened, 10 to 20 and 18 to 36 percent where only one did, and 39 and 55 of 300 with the screen itself. It needs the two attaches within about a millisecond. (3) Three or more screens on one terminal, two of which repaint in the same moment: on the wire another screen's repaint and a client's choice are the same attach, so a repaint can take the other's older size for a choice, and the terminal ends at an older size: one the resized window had before, or another window's. Every window whose own size is another, the resized one among them, draws it clipped with the notice. With three screens and one window changed twice 150 ms apart, runs of 40 rounds ended at that window's last size in 9 to 22 rounds when its screen acted first, and in 35 to 40 in the other orders: ranges of the runs made, not bounds. Reason: an attach may carry a size and leave the decision to herdr-core, while a resize sent by itself would take the terminal from whoever works in it. The cost is one new attach per pane per resize (well under a millisecond each against a local core, Probe c in decisions.md).
- A pane covered by a zoom stays attached but sends no credit, so its stream stops once herdr-core's 256 KiB window is full. It can still send `FACTS` when the host reports a color change. An answer its emulator makes while covered is dropped, so a program waiting for it can time out or keep waiting. Only queries still held back behind the full window are answered once the zoom ends. Both supported herdr-core versions answer device attributes, cursor position, text area size and terminal version themselves, so this affects only replies made by the pane's emulator. Reason: a zoom must cost the covered terminals no reflow, and no credit is spent on a picture nobody sees.
- Terminals in hidden tabs are not kept at a size, so an unviewed terminal may reflow. Reason: parked connections are the most complex pane code in comparable screens, and the cost is not worth it.
- Copy uses OSC 52 only, and the screen says so when the host cannot do it. Reason: opening clipboard helper programs would start a process, which the screen never does.
- Copy mode (`Ctrl+B [` by default) browses one pane's attach history. Use `h`/`j`/`k`/`l` or the arrows to move, `w`/`b` for words, `0`/`$` for row boundaries, `g`/`G` for the oldest and newest rows, and `Ctrl+U`/`Ctrl+D` for half pages. Use `v` or `V` to select characters or lines, then `y` to copy. Use `/` and Enter to find text, `n`/`N` to step through matches, and `f` to label up to nine URLs, paths, and hashes for copying. A fully visible target that soft-wraps gets a single label on its first cell. Hints omit logical lines cut off above or below the viewport, targets cut off at the sides, and tokens that may be split at a terminal margin. Reason: the core's attach replay can turn a wrap into a hard break, so a token next to such a break cannot be copied reliably.
- At the oldest kept row, replay may leave only the tail of a wrapped token. Hints skip that leading text unless a visible separator, a recognized URL scheme or an explicit home or dot path root establishes where the target begins. A slash at the left edge alone might be part of a longer path. You can still select the visible text and copy it by hand.
- Leaving Copy mode restores the pane's entry scroll offset. Escape leaves from any phase; `q` leaves unless the search field is open. A program exit ends Copy mode as its pane closes. A switch to the alternate screen ends Copy mode and the main screen gets its offset back when it reappears. A host resize ends Copy mode and restores the old picture while it is still displayed; the replacement attach starts at the newest rows. New output clears the active selection and hint labels because the rows the engine keeps can change. Search uses the engine's ASCII case folding.
- Kitty graphics probes get a refusal because the screen cannot draw them. On herdr-core 0.1.17, a probe gets no reply until the user has typed in the pane on that attach. That version has no automatic input, so sending a reply earlier could take the terminal's size from another viewer.
- On herdr-core 0.1.17, which has no automatic input, a program gets focus-in with the user's first input in the pane instead of at the pane switch (again after each new attach of that pane), and focus-out only when its pane leaves the shown tab. Reason: automatic input arrived in 0.1.18 and focus reports must never take a terminal's size.
- At 64 columns or fewer the screen draws herdr's narrow layout (its two-row header and switch button, the panes laid out as on a wide screen) and its switcher. The switcher's agents keep the screen's order and words (S7), and their second row names the agent's kind where herdr names the program it runs. Reason: herdr's own client switches to this layout at the same width, and a phone over SSH has 40 to 60 columns.
- `prefix+enter` opens herdr's menu on a wide screen and its switcher on a narrow one (herdr opens them by a tap only). Reason: a keyboard reaches them without a mouse.
- An empty core's first workspace opens at once, as herdr's server opens one, but in the folder the screen was started from (the folder `ovis tui` was typed in, which it passes as `OVIS_TUI_CWD`, else the screen's own working folder) and named after it, where herdr's opens in its server's home as `~`; started from the home it is `~` too. When the core cannot use that folder, the workspace opens in the core's own folder as `~` and the screen says which folder failed (`first_folder_unusable`). The folder gives way only when herdr-core refuses to start the shell there (`spawn_failed`); once a shell was started, nothing starts another. Several screens that find the core empty at once open one first workspace between them: a claim in Ovis's layout document decides which. The claim holds for 15 seconds from when it was written (`FIRST_CLAIM_MS`); its screen takes it out once the workspace is made or when it leaves, and one that died holding it leaves it to that time, after which another screen takes it. Opening the first workspace is a layout write like any other: what is typed meanwhile waits behind it (next line). Reason: a screen started in a project should start its first shell there, and a screen joins a core that may run with another home; herdr-core has no call that lists its clients, so a time is the only proof that a claim's screen is gone.
- While a layout write the user started is under way (a new workspace, tab or split, a close, a rename, a move, a swap, a zoom, the first workspace), what is typed, pasted or clicked into a pane waits behind it, in order, and goes through once a frame shows what the write did, to the pane it leaves in front. What waited is dropped with an `input_dropped` notice, never sent to the pane focused before, when the screen does not show that within 2 seconds (`LAYOUT_SHOWN_WAIT_MS`), and nothing more waits past 4,096 events or 1 MiB of text. Any other action, and a key or a press on a menu or another overlay, is refused when it is read, with one `layout_busy` notice per write. A right press is told apart when it is read (`rightPressGoes` in `tui/view/mouse.ts`): one that would open a menu is refused with that notice, one that meets nothing is dropped, and one for a program (a pane set to `Send right-clicks to pane` whose program reads the mouse) waits with the rest; the drag and the release of a refused press go with it. A release or a pointer move over a menu is refused without a word, and a detach never waits. herdr's client acts on its own server at once. Reason: herdr-core answers a layout call some milliseconds later, and a key read meanwhile must meet the layout the write leaves, not the one before it.
- The screen keeps, per core id, the focused workspace, the tab each workspace shows, the pane each tab shows and the pane looked at before, with the ids of the workspaces, tabs and terminals they were taken among, in a small file in its state folder (`view-<core id>.json` under `OVIS_TUI_STATE_DIR`, else `ovis-tui` under the XDG state folder; the folder 0700, the file 0600), written by rename whenever that view changes, never per frame. A rerun opens the same place; a place gone since gives way by the same rule a close does, and the screen says so (`view_moved`). Two screens on one core share that file and the last writer wins: the next run opens where the screen that changed its view last was. The file holds ids only: no name, no pane text, nothing typed. Reason: focus is each screen's own and herdr-core keeps none, and a screen has no identity of its own to keep a file per screen.
- The screen refuses to run inside one of its own panes. Reason: it would draw itself into itself.
- Escape and `ctrl+[` after the prefix always cancel it. A binding of the config on either key after the prefix is dropped with a `cancel_key` note, so the help, the mode bar and the keys agree. Reason: one key always backs out of a prefix, whatever the config binds.
- `ctrl+alt+g` locks the screen (herdr has no lock): every key, the prefix included, goes to the focused pane until `ctrl+alt+g` again or a tap on the LOCKED badge. It is a fixed screen key, given to the lock only while nothing of the config holds it; a config binding keeps it with a `lock_taken` note, and there is then no lock. Reason: a program in a pane may need the prefix itself, and the chord never reaches the program.
- herdr's `open_notification_target` (`prefix+o`) jumps through the agents that need the user, blocked ones first, then done ones, each the longest in that state first; `next_agent`, `previous_agent` and `focus_agent` go by the screen's agent order (the browser's, which the switcher shows; the sidebar shows herdr's). Reason: one order across workspaces that says whose move it is (cluster 7).
- The screen draws like herdr's own TUI (visual-parity.md) except for four looks outside the sidebar: an agent's entry in the switcher keeps its content and the browser's order (S7), a state keeps its own glyph so it never shows by colour alone (S8), the colours are the theme's, picked from the host's background, with a background behind every chrome cell (C1), and the words are the web's (C2). The sidebar is herdr's in all four: its two-row agents by workspace, its dots, no background of its own, and its lower-case words. Reason: one order and one set of state words with the browser, a state that reads without colour, and one theme across Ovis; the sidebar is herdr's so that the screen reads like herdr's at a glance. The parity cases (`tui/view/parity.test.ts`) compare the kept cells on place, shape and colour role and the sidebar whole.
- The sidebar and its rail draw herdr's own colour values, which its default theme writes there on any host, dark or light: yellow working, red blocked, teal done and green idle dots, a mauve branch in front, its two greys and a near-black row in front (on a light host too). Everywhere else the screen keeps the theme's colours. Reason: the sidebar is meant to look like herdr's on any host; the parity cases compare the sidebar's colours as values.
- The sidebar's branch row shows the branch alone, where herdr adds the ahead and behind counts against the upstream: those need git's object store, and the screen reads only `.git` (walking up from the folder of the workspace's first pane, following a linked worktree's `.git` file) and `HEAD`, with no process. A detached HEAD shows its commit's first seven characters. The branch is read again each time the core's view changes, at each key into a pane and at each focus change, so a branch switched in a pane shows at the next key or focus change. Reason: the screen starts no process and never asks the Ovis server, which alone runs git.

- herdr keeps a pane's `Send right-clicks to pane` in its server, for every client; the screen keeps it in Ovis's layout document beside the tab's zoom (`passthrough`), and a repository's folded worktree group there too (`collapsed`), so every screen on the core sees both. Both are kept per pane and per workspace against what lives in the document now (`server/herdr-core/layout-doc.ts`): a pane moved to another tab keeps its setting there, and an edit by another screen or the browser does not drop it. The browser reads neither. Reason: herdr-core keeps no such setting, and the layout document is where the screens' shared layout already lives.
- The right-click menus were measured at 120x40 and 80x24 only; the narrow layout's right press was not captured, and the screen opens the same menus there. Reason: herdr's narrow layout has no sidebar (visual-parity.md R1-R8).

## Left out on purpose

- Floating popups. Cluster 18 names them and they are left out on purpose. Reason: their lifecycle is the subtlest part of any pane feature in the terminal screens studied for this design.
- A settings overlay that writes configuration back, and herdr's sidebar token grammar. Reason: config write-back and a second grammar are costs the first release does not need.
- herdr's right-click `New worktree` and `Delete worktree checkout...`. Reason: both run git, and the screen starts no process and never asks the Ovis server, which alone runs git for Ovis. The other worktree entries are built: `Open worktree...` reads the repository's checkouts from git's own files, and `Close group` and `Collapse`/`Expand` work on Ovis's layout document.
- A submodule's workspace and a linked worktree of a bare repository list no checkouts: their `Open worktree...` answers `not_git_worktree`. Reason: git's files name no main checkout there to list first (a submodule's git folder is under its superproject's `modules`, a bare repository has no checkout of its own), and the screen reads those files rather than running git. herdr's `Use Herdr right-click menu` reads `Use the right-click menu` (C2: the screen's own word; herdr's captures never show it).
- A hover reaches a pane's program only from the viewer whose size is the terminal's. With two viewers of different sizes herdr resizes the pane to the hovering client and delivers every client's hover; the screen delivers a hover only while its own size is in force and drops it otherwise. Reason (forced, P6): the screen never takes a terminal's size from another viewer until the user types in it, and a hover is no typing.
- herdr's `ui.right_click_passthrough_modifiers` (unset by default: no modifier sends a right press to the program). Reason: the screen reads herdr's `[keys]` table only; with herdr's default, `Send right-clicks to pane` is the way, as in herdr.
- herdr's `edit_scrollback` (`prefix+e`) and `clear_pane`: a bound key gives one `not_built` notice per press. Reason: `edit_scrollback` opens the scrollback in an editor program, and the screen starts no process; herdr clears a pane through its own server, herdr-core has no call for it, and typing a clear into the program is not the same.
- Terminals of other herdr-core machines. Reason: the screen shows the core it is connected to, though every identity carries a machine part, so another machine's terminals could be listed later without changing the model.
- Opening links and clipboard helper programs. Reason: both start a process.
- Sound and system notifications. Reason: not required by any cluster, and the browser and phone UI already notify.
- Translation. Reason: every string lives in one table so translations can follow later.
- An import from herdr: Ovis's web UI already has "Move everything to herdr-core", and the screen adds no import of its own (cluster 27). Also left out: per-agent CPU and cost columns and file preview. Reason: herdr-core reports no usage or cost, and a file preview belongs to the browser.
- Plugin or mod support. Reason: the screen adds no extension format.

## How the screen is compared with herdr

The screen's picture is compared cell by cell with captures of herdr 0.9.5's own client in `tui/view/parity.test.ts`: the same scenes, at 120x40, 80x24, 64x20 and 45x30, in both palettes. The captures are made by `tui/testing/herdr-capture.ts` against a real herdr and stored under `tui/testing/herdr-captures/`; `tui/testing/herdr-reference.ts` drives herdr and the screen side by side in two pseudo-terminals for a manual comparison. What a comparison leaves out or carries over is named by its line in [visual-parity.md](visual-parity.md). The behaviour against a real herdr-core (0.1.17 and 0.1.18) is checked by the live tests (`*.live.test.ts`), which run when `OVIS_TEST_HC_BIN` names an hc binary.
