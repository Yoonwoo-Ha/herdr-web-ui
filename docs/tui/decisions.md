# Terminal screen: decisions and probe results

This file records the design decisions behind Ovis's own herdr-core terminal screen, with their reasons, and the results of the probes that were run before it was built.

## Decisions

- D1: the screen is written in TypeScript inside the Ovis repository and its existing compiled binary, on the in-tree libghostty-vt wasm, reusing the herdr-core client and model in `server/herdr-core`. Reason: the release pipeline stays the same, the layout and state rules exist once, a Windows binary already exists and CI runs on the existing runners. The known weakness: Bun's terminal I/O has regressed between versions.
- D2: the screen talks to herdr-core only. It never asks the Ovis server anything and gets no Ovis token. Things only the Ovis server knows (question cards, readable last turn, pins, automatic tab names) are not built; an agent's question is answered by entering its terminal, as in herdr.
- D3: Windows comes last. It adds an `ovis` command on Windows and checks keyboard, mouse, paste and resize on Windows; whatever does not pass is reported, and Windows then prints one line instead of opening the screen.
- D4: with no herdr-core running, `ovis tui` at a terminal asks whether to start it. Enter or y starts the core with an environment scrubbed of Ovis secrets and herdr pane ids and opens the screen; n prints the start command and exits. Nothing starts a core without that yes. Reason: a core outlives the screen and holds the user's terminals, so starting one is the user's choice.
- D5: no herdr code is copied or translated. herdr, hc-tui and rodeo are read as descriptions of behaviour only, and every line is written new.

## Defaults

- A2: `ovis tui` opens the screen; `ovis status` is unchanged. `ovis --help`, `ovis --version` and what plain `ovis` does stay the command line's own (`scripts/plugin-cli.ts`): `ovis tui --help` is answered there, and the screen is started before the command line reads the install's state.
- A3: keys follow herdr's bindings through `shared/herdr-keys.ts` (the user's herdr config when present, herdr's defaults otherwise), with prefix ctrl+b, so that the screen feels like herdr.
- A4: the hc-tui based client in `crates/ovis-tui`, its pin, patches, workflow and notices are removed once `ovis tui` opens this screen and it has passed the rule tests carried over from that client.
- A5: outside the sidebar, status words and colours follow Ovis ("Needs you", "Working", "Done", "Ready"; theme tokens from `src/styles.css` through the generator); the sidebar uses herdr's own words and colours ([parity.md](parity.md)).
- A6: screen text is English first, with every string in one table so translations can follow; the screen sends no telemetry.
- A7: tests are written first for every pure module (decoder, reducer, layout, painter, attach machine) and with the change for IO glue; user-visible behaviour is also checked on a real isolated core in a pseudo-terminal.
- A8: left out, each with its reason in [parity.md](parity.md): floating popups, multi-repo worktree creation, import from herdr, resource and cost columns, plugin or mod support, a browser pane, sound.

## Probe b
- b1: the callback route delivers replies in the source and the compiled form: a 105-byte hand-written helper module whose exports call JS imports, `__indirect_function_table.grow(3)`, `table.set`, then `ghostty_terminal_set` with USERDATA 0 (the pane number), WRITE_PTY 1, SIZE 6 and DEVICE_ATTRIBUTES 8, read by name from `ghostty_type_json()`; CSI 6n gave `ESC[1;4R`, DA1 `ESC[?64;22;52c` from our callback, `?2048h` `ESC[48;24;80;384;640t` and the resize to 100x30 `ESC[48;30;100;480;800t`. Rule: one helper module per process, three table slots per engine instance, replies routed by userdata.
- b2: in legacy mode ctrl+shift+a gives 0x01 only when the event's utf8 text is the unshifted letter `a`; utf8 `A` gives `ESC[97;5u` and no utf8 gives nothing, whatever the unshifted code point or consumed mods. Rule: for a chord that holds ctrl, set utf8 to the unshifted text and `unshifted_codepoint` to the same letter, keep shift in mods, and call `setopt_from_terminal` before each encode; kitty flag 1 then still gives `ESC[97;6u`, legacy ctrl+c 0x03, legacy alt+a `ESC a`.
- b3: search and selection text work: `search_new`, `search_set(NEEDLE)`, `search_run`, `search_get(TOTAL_MATCHES, MATCHES)` found needle-07 in the scrollback (SCREEN row 6, no ACTIVE or VIEWPORT point: NO_VALUE -4) and needle-38 on screen (ACTIVE row 3), and `terminal_selection_format_alloc` and `_buf` returned `needle-07 end07\nL08 needle-08` for a selection over two lines. Rule: place matches with `point_from_grid_ref(SCREEN)` and treat NO_VALUE for VIEWPORT as off screen.
- b4: per-pane. RSS for 1, 4 and 16 terminals of 120x40, 1 MB of output each, SCROLLBACK_MAX_LINES 2000 and the byte limit removed (1963 rows kept in every terminal), min-max of 3 runs per form: shape A (one instance) 70.8-78.0, 79.1-82.0 and 102.5-107.4 MB (wasm 3.3, 10.4, 38.9 MB); shape B (one instance per terminal) 69.7-79.5, 78.8-89.7 and 141.4-150.4 MB (wasm 3.3, 13.3, 53 MB), all well under 400 MB. Earlier numbers, line limit only, about 430 rows kept: A 61.9, 74.9, 82.7; B 72.9, 79.7, 108.3 MB. A wasm trap is a catchable `WebAssembly.RuntimeError` and the other 15 terminals still answer in both shapes, but each trap leaves `__stack_pointer` about 17.7 KB lower; after ten more, no terminal in that instance answers (0/16 in shape A) unless the saved value is written back. Rule: one instance per pane; set SCROLLBACK_MAX_BYTES together with SCROLLBACK_MAX_LINES (the default byte limit of 10000 keeps about 430 rows of 120 columns); after a trap, drop that pane's instance and rebuild the pane by reattaching.
- b5: herdr-core (hc 0.1.18) gives every program TERM=xterm-256color, COLORTERM=truecolor and TERM_PROGRAM=ghostty, whether the core was started with no TERM or with another one. XTGETTCAP TN gets no reply until TERMINFO_NAME (option 37) is set; set to xterm-256color, it answers `DCS 1+r544E=787465726D2D323536636F6C6F72 ST`. Rule: set TERMINFO_NAME to xterm-256color on every pane's terminal.

## Probe c
- c1: 0.1.18: a unix socket opened from Bun (`node:net`) and handed to `HcConnection` as an `HcTransport` answers `hello` without `hc connect` in 0.3 ms; an absent socket file fails with ENOENT and a stale one with ECONNREFUSED, both a clean `no_core` error within 5 ms, and a stand-in `hc` first on PATH logged nothing. 0.1.17: the same. Rule: the screen reaches the core through its socket alone; no core means `no core`, and nothing is started.
- c2: 0.1.18: A (no `resumed`) 120x40, then B (`resumed`) 80x24: the terminal stays 120x40, with no `size` event, and B's attach reply says 120x40; B alone (`resumed`) on a terminal nobody views: 200x120 -> 80x24; A (`resumed`) 120x40, then B (`resumed`) 80x24, nobody typing: 80x24, the newest attach wins, and 120x40 again when B leaves. 0.1.17: identical in all three cases.
- c3: 0.1.18: the first DATA starts with CAN (0x18) and the paint ends with `CSI 0m CSI ?9001l`; `history: 2000` is honoured (lines 1-300 come before the 24-row screen: 324 LFs, against 23 with history 0). 0.1.17: byte for byte the same. Rule: the first paint ends at the 9001 mark inside the stream, not at a frame boundary (detail below).
- c4: 0.1.18: when the program ends, its last DATA comes first, then about 60 ms later the CLOSE `{"exit_code":3,"finished_ms":<ms>,"reason":"exited","signal":null}`, with the `finished` event carrying the same data; `terminal.kill` while attached gives CLOSE `{"exit_code":null,"finished_ms":<ms>,"reason":"killed","signal":1}` and `finished`; a kept program that dies by a signal gives CLOSE `{"reason":"signaled","signal":9,"exit_code":null,"finished_ms":null}` with `lost`, then `restarted` 2.1 s later; a viewer's own CLOSE gets an empty CLOSE back within 0.1-0.3 ms. 0.1.17: the same. Rule: a CLOSE with `finished_ms` set means Ended; `signaled` with `finished_ms` null means Waiting for `restarted`; our own CLOSE is settled by the empty answer.
- c5: 0.1.18: while A (driving) resizes 120x40 -> 100x30, B (`resumed`, 80x24) gets no RESIZE frame, one `size` event (100x30) and, within 1 ms, the program's own bytes laid out for 100x30, with no repaint (no CAN); B's close-then-attach takes a median of 0.27 and 0.24 ms (two runs), and the paint is complete 10 times out of 10 (CAN first, the 100x30 screen, the 9001 mark). 0.1.17: the same, median 0.30 and 0.22 ms, 10/10. Rule: closing the attach and attaching again stays the one repaint routine, and its cost is negligible.
- c6: 0.1.18: a terminal from `terminal.run` that was never attached is 200x120, and after every viewer left it returned to 200x120, with a `size` event. 0.1.17: the same. Rule S6 (as `tui/core/pane.ts` cites it): the pane takes `actual` only from the attach reply and `size` events.
- c7: 0.1.18: `hello.features` lists `automatic_input` and the attach reply says `automatic_input: true`; B's AUTOMATIC_INPUT `ESC[I` reaches the program (1b5b49) and the size stays 120x40, while the same bytes as DATA, and FOCUS 1, take 80x24 (FOCUS 1 also hands a 1004 program `ESC[I`); FOCUS 0 hands it `ESC[O` and takes nothing. 0.1.17: no `automatic_input` in hello or in the reply; a kind 6 frame sent anyway is dropped (no bytes reach the program, the size is kept); DATA and FOCUS behave as on 0.1.18. Rule: the automatic-input focus contract on 0.1.18, the fallback focus contract on 0.1.17.
- c8: 0.1.18: with A driving at 120x40, B's FACTS frame leaves 120x40, and B's attach with `display` and `resumed: true` leaves 120x40. 0.1.17: the same. Rule: neither takes the size on either version, so the fixed fallback (attach without `display`, FACTS only with a take) is not triggered; the attach may carry `display`.

Run on 2026-11-16 with Bun 1.4.2, against hc 0.1.18 and hc 0.1.17 (the release archive, its SHA-256 checked before unpacking). The probe code was throwaway.
- Each version ran twice, each run in its own core: a `mkdtempSync` folder under TMPDIR, `isolatedHcEnv`, HC_SOCKET checked to be inside it, HC_SESSION `t<pid>`. Both runs gave the same answers; only timings differed, plus the arrival order of one `size` event in c4.
- Failure scenario (no core started): the absent and stale sockets both gave `no_core`, and the stand-in log stayed empty (0 bytes); a control call to the stand-in was logged.
- An attach reply's `terminal` has the size as it is once that attach is applied: B's reply said 120x40 beside A, and 80x24 alone.
- A same-size RESIZE is a stamp. B (`resumed`, advertising 80x24) sent RESIZE 80x24 and took the size from A, who was driving. A RESIZE 120x40 from B, equal to the current size, also stamped B: D then attached (`resumed`) at 70x20, A left, and 120x40 stayed. Both versions.
- A RESIZE from B alone, with no DATA, takes the size (90x28), on both versions.
- `terminal.attach` at the terminal's current size sends no `size` event. Without `resumed` it stamps: C attached at 120x40, B (`resumed`) at 80x24, A left, and 120x40 stayed. With `resumed` it does not: the same steps gave 80x24, the newest unstamped attach.
- c3 bytes, the same on both versions for history 0 and 2000. First 16: `18 1b 5b 21 70 1b 5b 3f 32 30 32 36 6c 1b 5b 3f` (CAN, CSI !p, CSI ?2026l, ...). Last 16 of the paint: `34 3b 38 48 1b 5b 30 6d 1b 5b 3f 39 30 30 31 6c` (...4;8H, CSI 0m, CSI ?9001l). The paint up to the mark was 379 bytes with history 0 and 1691 bytes with history 2000; with the shell's 12-byte redraw that follows it, 391 and 1703 bytes.
- The 9001 mark ends the paint, but not always a frame. The shell's 12-byte redraw after the attach resize (`CR CSI K CR probe$ `) can arrive in the same DATA frame as the paint (one 391- or 1703-byte frame) or in the next frame (after a 379- or 1691-byte paint frame); which one is timing, seen on both versions. The attach code must split the stream at the mark, inside a frame.
- c4 timings: the CLOSE came 56-61 ms after the program's last DATA, and 56-63 ms after `terminal.kill`. `finished` arrived on the event connection 0.1-0.3 ms before the CLOSE on the attach connection. Restart after loss took 2.08-2.13 s. The README's CLOSE example has no `finished_ms`; both versions send it, null after a loss.
- Both versions list `resize_notifications` in hello. The reply said `resize_notifications: false` because no attach asked for it (no `observe` was used).
- On the 0.1.17 release binary a FACTS frame took no size.
- On 0.1.17 `channel.writeAutomatic` sends DATA (the channel is not confirmed), and DATA takes the size, as the fallback contract expects.
- The core does not filter kind 6 bytes. On 0.1.18 a kind 6 `ESC[I` reached a program that had NOT turned mode 1004 on (it got 1b5b49), while FOCUS 1 gave that program nothing (and took the size); on 0.1.17 the kind 6 frame was dropped and FOCUS 1 likewise gave nothing. So the screen must check mode 1004 in its own emulator before it writes a focus report through `writeAutomatic`.
- FOCUS 0 from a viewer that never sent FOCUS 1 still hands a program with mode 1004 on `ESC[O` (1b5b4f) and takes no size (120x40 kept), on both versions. So the screen sends FOCUS 0 only on a channel that got FOCUS 1 from it.
- Every core was stopped with `hc server stop` in its own environment. Its pids (core and holder) were gone afterwards, `test ! -S` on its socket was true and its folder was removed. The probe's first version could exit before that stop had run when it was signalled mid-run; its cleanup is now one shared promise that the signal handlers, the time limit and the final `finally` all await. Signalled on each version with SIGTERM right after the core started, after `OK c2`, after `OK c4`, after `OK c6` and during c8, SIGHUP after `OK c3` and SIGINT after `OK c5`, the probe exited 143, 129 and 130, and every time its core and holder were gone, its socket was gone and its folder was deleted: no core was left on either version.

## Probe d
- d1: first frame, the entry as source (`bun entry.ts`): median 40.0 ms (min 35.9, max 43.6, n 10; rerun median 37.1 ms), at load average 44.
- d2: first frame, the compiled binary run directly: median 31.0 ms (28.2-37.3; rerun 26.4 ms), at load average 44.
- d3: first frame, the compiled entry as the child of a compiled parent that stays (SIGINT ignored, SIGTERM and SIGHUP passed on): median 41.3 ms (37.3-54.8; rerun 35.8 ms), at load average 44, well under 400 ms.
- d4: first frame through `process.execve`: median 41.6 ms (38.3-46.3; rerun 34.9 ms), recorded only. Importing `scripts/plugin.ts` without running a command costs 52.3 ms in-process (47.9-56.3), or 63.7 ms for the whole Bun process against 7.8 ms for an empty one, so the launcher must decide before that import.
- d5: RSS (VmRSS): idle parent 23.8 MB (23.8-24.9); child with the bare entry 53.5 MB; child with one empty 120x40 terminal (scrollback limit 2000 lines, 0 rows kept) 57.9 MB (57.5-58.9), 78.6 MB once fed 1 MB (1635 rows kept); child with four such terminals, each fed 1 MB (1634-1640 rows kept each), 85.8 MB (84.1-87.3). 2000 is the limit, not the amount kept.
- d6: raw-mode `data` chunks are whatever the kernel hands over. A 1 MiB bracketed paste arrives whole (same sha256, 10/10) in 44-131 chunks (median 86.5) of 196 B to 180 KB within 10-33 ms, and 3-9 chunks per paste end inside a UTF-8 character (three runs of 10; the next chunk starts with the rest of it). U+D55C U+AE00 arrives as written: one write gives 1 chunk, a write cut mid-character gives `ed95` + `9ceab880`, byte by byte gives 6 chunks. 200 SGR mouse reports (2350 B) come in one chunk. Read as bytes, Bun never rejoins a character, so the input framer `tui/input/framer.ts` must do it.
- d7: (a) a write to a stalled terminal blocks the loop: `process.stdout.write` of 4 MiB returned true after 2936 ms (2879-3123), with no `drain`; the 10 ms timer's longest gap was the same 2944 ms, and a key typed 1 s in was read only after the write returned. (b) stdin can be drained without blocking and without loss, but only as far as Bun has already read it. The call: `process.stdin` paused with a `readable` listener, then `read()` until null. Bytes that waited while the loop was idle come back at once (3000 of 3000 B in 0.14 ms, 10/10). With 3000 B typed during a 400 ms busy loop turn, the call returned 0 B in the same tick as `setRawMode(true)` (and also when raw mode was set before that turn) and after one `setImmediate` turn. It returned all 3000 B after two or three turns, or after waiting for one `readable` event (the wait: medians 0.8-2.1 ms, single runs 0.7-3.3 ms; up to 6.9 ms in a second, independent set of runs), 10/10 in source and compiled form; no byte was lost in 400 runs. With 0 B waiting it returns null at once (at most 0.4 ms), and the `readable` wait ran to its 50 ms bound. So a drain at one moment must first let the loop turn: a wait for one `readable` event with a short bound worked every time for 3000 B, and two turns were enough in every run.
- chosen start shape: the screen as a child of the launcher (median 41 ms; execve, median 42 ms, recorded only)

Run 2026-11-16 with Bun 1.4.2 on linux-x64 (AMD Ryzen Threadripper PRO 3995WX). Load average: run 1 43.8 at its start and 58.7 at its end; run 2 40.8 and 43.6; run 3 (a rerun of the split count, drain timing and kept rows) 44.4 and 40.8. Every start time was measured under that load, so they are upper-range numbers. The probe code was throwaway.
- First frame: timed from just before fork+exec of the launched process (Python `time.monotonic()`) to the pty-master read that delivered the first frame's closing `ESC[?2026l` (1b 5b 3f 32 30 32 36 6c). That marker was checked to come after `ESC[?2026h` and `frame=1`; nothing the probe logged about itself was used. Each run used a fresh 80x24 pty with the probe as session leader, and every run exited 0 with the terminal restored.

- Build: `bun build --compile --minify --bytecode --format=esm --target=bun-linux-x64 main.ts` gives one binary. No argument runs the entry, `--parent` runs a parent that stays (the shape the launcher of `ovis tui` had then), and `--execve` makes it execve into itself.

One strace run (`trace=%file,%process`) showed no path under the user's home other than the checkout, the probe, the scratch folder, their parent directories and the bun binary. - d5 setup: VmRSS was read 200 ms after the first frame. The feed was mixed output (SGR, truecolor, Hangul, CJK, emoji, long wrapped lines, CR overwrites) in 64 KB writes, with `Bun.gc(true)` before the frame and one module instance for all terminals. No feed kept 2000 rows: 1.0, 1.3, 1.5 and 2.5 MB kept 1635, 1741, 1662 and 1648 rows (RSS 78.0, 78.9, 79.1 and 83.0 MB; 3 runs each above 1 MB).

- d6 failure scenario: the feeder cut U+D55C after 2 bytes, 30 ms apart. Read as bytes, the probe got `ed95` then `9ceab880`, 10/10: Bun does no decoding on a Buffer stream. With `setEncoding("utf8")` the same writes gave one 6-byte string with no U+FFFD, and byte-by-byte writes gave `ed959c` and `eab880`. The framer works on bytes, so rejoining is its job.
- d7a: 4 MiB went out in one `process.stdout.write` while the harness read nothing for 2 s. The call itself blocked about 2.9 s (Bun writes to a tty synchronously) and `writableNeedDrain` stayed false. The screen's loop should hand stdout one frame at a time and not expect `drain`.
- d7b, the other methods: `process.stdin.read()` with no listener and `new tty.ReadStream(0).read()` returned null even with 3000 B waiting. `Bun.stdin.stream()` raced against `setImmediate` returned the 3000 B in 0.3 ms, but left a pending read that takes the next bytes. Reopening `/proc/self/fd/0` with O_NONBLOCK, or setting O_NONBLOCK on fd 0 through bun:ffi `fcntl`, read the 3000 B and then got EAGAIN (0.3-0.5 ms). Both compete with Bun's own reader, and fcntl changes a flag the shell shares. A plain `fs.readSync(0)` blocked until a byte arrived (2000 ms, when the harness typed one).
- Note: a `process.on("SIGUSR1")` listener does not keep a Bun process alive. The drain probe with no other handle in its loop exited 0 on its own 13.0-15.5 ms after start (10/10, never signalled), so in the first pass the signal met a process that had already exited. With a 50 ms interval running, the handler always ran.
- SIGKILL of the d3 child: the parent exited 137 (Bun's 128 + 9). `stty -a` then showed cooked mode (icanon echo isig), but no `ESC[?1049l` was written, so the alternate screen and the hidden cursor stayed. Control: the entry killed with no parent left the pty raw (-icanon -echo). So the cooked modes came from the parent Bun's own exit restoring the termios it started with; strace showed it (`TCSETS2` on fds 0-2 just before `exit_group(137)`). A launcher that stays as the parent must still leave the alternate screen and undo the modes.
- d7 drain beyond one tty buffer: more than the tty holds (13.8-15.9 KB here) needs more than one wait: with 65536 B typed, one wait returned all of it in 49 of 60 runs and only the first 13.8-65.0 KB in 11; repeating wait-and-read until a 50 ms wait timed out returned all 65536 B in 100 of 100 runs (a second, independent set of runs).
